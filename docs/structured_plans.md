# 结构化技能计划（5B）

## 接口与职责

`/execute_task` 保留已安装模板入口。新增 `/execute_plan` 使用 `robot_interfaces/action/ExecutePlan`，允许规划器提交技能级顺序计划。两者共用一个活动目标、同一个单线程执行引擎与资源管理器；任一入口忙碌或故障锁定时，另一个也拒绝任务。

| 字段 | 含义 |
|---|---|
| `schema_version` | 当前为 1；其他版本拒绝 |
| `steps` | 1～32 个 `SkillStep`，按顺序执行 |
| `skill_id` / `implementation_id` | 已注册技能及该技能的一种实现 |
| `argument_names` / `argument_values` | 名称和值一一对应，名称不可重复；现阶段最多两个必填 entity_id 输入 |
| `timeout_ms` | 整个计划的期限，1～600000 ms |
| 反馈 `step_index` | 当前技能的索引，从 0 开始 |
| 结果 `completed_steps` | 报告验证成功的技能数量，包含只读定位；不代表物理动作全部回滚 |

组件接口版本、目录版本和计划版本分别管理，不能互相替代。技能级期限继续使用运行时的 `skill_timeout_ms`，停止等待使用 `stop_timeout_ms`。

规划器决定技能、目标和实现；组件配置由运行时绑定。调用者不能提供 XML、脚本、任意行为树节点或驱动命令。运行时只从通过校验的标识符和参数生成 `Skill` 节点，再使用 BehaviorTree.CPP 顺序执行。

## 全计划校验与执行期检查

核心 `validate_plan` 不依赖 ROS/BT，且不会构造技能、获取资源、调用许可门或写入预期效果。它首先检查版本和步数，再校验每一步的输入模式、实现依赖和配置实体。

现有五种技能的顺序语义为：

- `locate_object` 可定位任一配置实体。
- `pick_object` 要求对象角色、此前在本计划定位该对象，以及逻辑上空闲的夹爪。
- `place_object` 要求持有同一对象、目标角色，以及此前在本计划定位该目标。
- `verify_grasp` 要求逻辑上持有对应对象；执行期仍须取得动作后的稳定证据。
- `verify_placement` 要求匹配目标的释放候选，可来自本计划前序放置或实际保留状态；验证步骤消费该候选，不能重复消费。

校验器从当前 `WorldState::attached_object` 开始推演持有状态，但只在临时变量中推演。已有观测不替代计划中的定位步骤；取消或失败后仍以实际保留的持有状态为准。支持已持有对象时的“定位目标→放置”计划，也支持仅定位或以抓取结束的计划。

后续步骤非法会在接收前拒绝整个计划，不会先执行前面的动作。拒绝原因在运行时日志中带步骤索引；当前 Action 拒绝没有结构化错误正文。

接收后的每一步仍通过 `Session` 和技能实现检查执行许可、资源、观测时效、夹爪持有状态、到位容差和停止反馈。计划校验不保证路径可达或传感器有效；耗时步骤可能使先前定位过期，这时执行失败。模型预测的抓取、释放和位置不会被写成实际观测。

任一步失败即停止顺序推进。取消和超时先于下一次技能推进处理；只有测量停止确认后才释放资源。未知状态仍锁定执行。没有自动重规划、自动重试、动作回滚或持久幂等账本。

## 确定性规划示例

启动 mock 或 Panda 示例，source ROS 和工作区 overlay 后运行：

```bash
python3 scripts/plan_pick_place.py --object workpiece_two --target tray_two --dry-run
python3 scripts/plan_pick_place.py --object workpiece_two --target tray_two --timeout-ms 5000
```

Panda 使用 `--timeout-ms 90000`。`--dry-run` 只查询目录并打印技能计划，不提交执行。

客户端从 `/get_catalog` 检查输入模式、对象/目标和实现绑定，然后分解为“定位对象→抓取→定位目标→放置”。这只是针对已支持目标的确定性分解，不是通用搜索或 PDDL 求解器。目录校验后仍可能因运行时忙碌、持有对象或动态条件而被拒绝。

客户端只提交一次。结果等待超时不表示机器人已经停止；它报告状态不明，不重新发送计划。

6B 增加 `--verify-outcomes`，分解为六步并使用 `ManipulationObserver` 证据验证抓稳和放置。默认四步不变；当前证据为合成示例。步骤、来源与样本窗口见 [感知证据与结果验证](perception_verification.md)。

## 后续规划器、VLM 与 VLA 接入

传统规划器或 LLM/VLM 任务规划器可将输出转换成同一个技能计划协议，遵守目录参数和全计划校验；不能绕过运行时直接控制设备。目前没有模型 SDK、API key 或某个模型专用接口。

连续动作的 VLA 仍属于动作策略组件或独立技能实现，不把每个高频动作采样都塞进技能计划。新的实现需要满足共享的技能成功语义、停止与资源契约。新的技能语义需要增加明确的计划校验规则和测试，文字前置条件不会自动被解析。

今后根据实际需求再扩展参数类型、条件分支、世界状态快照和重规划。当前版本维持顺序计划、五种技能、配置位姿与 GenericSystem 的验证边界，没有真实视觉、物体接触或实机验证。
